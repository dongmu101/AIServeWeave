# Agent CLI 运行时性能优化（P2）

Status: ready-for-agent

来源（2026-11-18）：对 Agent 中 Claude Code 与 Codex CLI 运行时的稳定性与性能检查。P0（放宽误伤上限、启动参数、失败分类、登录刷新冲突）与 P1（未知事件、优雅终止、stderr 分类、轻量健康检查）已交付。P2 的量化手段也已交付：回合分段计时、`agent_cli_*` 指标与离线基准 `TestCLIStartupBenchmark`，见 [Agent README「本机 CLI 回合分段计时」](../../service/aiServeWeaveAgent/README.md#本机-cli-回合分段计时)。

本规格定义的 P2 优化项都**由数据决定是否启用**：先用已上线的计时采集线上分布，每一项只有达到启用门槛才实施，否则附上数据关闭为 `wontfix`。

## 问题陈述

经 Gateway 使用 Claude Code 或 Codex 订阅的调用方，首 token 明显慢于直连上游，而运维无法判断慢在哪里、该优化什么。

- **Claude 运行时**：每个回合都要冷启动一个 CLI 进程（本机约 0.19 秒，每回合约 266 ms CPU、约 222 MB 内存）。CLI 在发出模型请求之前，还要先等完约 3–5 个发往 api.anthropic.com 的请求（组织策略、远程设置、功能开关等）。Agent 的每进程代理每次都新建上游连接，所以每个回合都要多付一次握手加上这几次网络往返。上游不可达时，CLI 会卡在这一步重试约 18 秒。
- **Codex 运行时**：每个请求冷启动一个 app-server（本机到能接收回合约 60–160 ms，约 93–145 MB 内存），每个请求都是新的 ephemeral 线程。源码显示提示缓存的 key 取自线程 ID，跨请求的缓存亲和性可能因此丢失，代价是更高的首 token 延迟和输入费用，但还没有数据证实。
- **账户额度**：额度信息要靠额外起 CLI 进程（`get_usage`、`account/rateLimits/read`）定期查询，而 Claude 回合的响应头里其实已经带着同样的信息。

运维需要的是：知道每项优化能省多少，只做值得做的，而且任何优化都不能让请求更容易失败。

## 方案

按「先量化、再按门槛实施」推进，每一项都用同一套计时验证效果：

1. **采集基线**：部署带分段计时的 Agent，按运行时采集 1–3 天的分布。Claude 看 `cli_ready_ms`、`request_sent_ms`、`first_event_ms`；Codex 看 `history_injected_ms`、`turn_started_ms`、`first_event_ms`；另外看用量记录里 Codex 的缓存读取占比。
2. **Claude 同账户共享上游连接**：同一个运行时（同一个账户目录）的所有回合共用到 api.anthropic.com 的连接，启动请求与模型请求都复用已建好的连接，不同账户之间不共用。
3. **Codex 预热进程**：每个运行时预先启动少量已完成初始化与登录确认的 app-server，请求到来时直接使用；用完照旧销毁，「一个请求一个进程」的隔离不变。
4. **Claude 预热进程**：先做原型，确认在请求到来之前就能启动 CLI，并让它完成启动请求，同时不改变上游实际收到的请求；原型通过后再实施。
5. **Codex 缓存亲和性**：只做测量，确认多轮会话的缓存命中率是否明显偏低；改造方案另立规格。
6. **用响应头更新 Claude 账户额度**：用每进程代理已截获的额度响应头更新账户额度状态，减少专门查询额度的进程。优先级最低。

每项都有启用门槛和成功标准（见实现决策），不达标就关闭并记录数据。每项优化都必须能静默退回现有的冷启动路径：优化本身出错时，请求照常走原路径，不会因此失败。

1. 作为平台运维，我希望知道每个运行时首 token 延迟里有多少花在 CLI 启动、启动请求、上游连接和模型本身上，以便把优化投入到真正耗时的地方。
2. 作为平台运维，我希望每项性能优化都有事先写好的启用门槛，以便按数据而不是凭感觉决定做不做。
3. 作为平台运维，我希望没达到门槛的优化项附上数据关闭，以便以后重新评估时有依据。
4. 作为平台运维，我希望优化前后用同一套指标对比，以便确认优化真的生效。
5. 作为平台运维，我希望在每个节点的 `/metrics` 上按运行时看到各阶段耗时的分布，以便和 Gateway 的 TTFT 指标对照。
6. 作为平台运维，我希望不花额度、不联网就能在任意主机上复现冷启动基线，以便比较不同 CLI 版本和不同硬件。
7. 作为 Agent 节点运维，我希望 Claude 回合的启动请求复用已建好的上游连接，以便每个回合少一次 TLS 握手。
8. 作为 Agent 节点运维，我希望不同订阅账户之间从不共用上游连接，以便账户之间不会在连接层面被关联起来。
9. 作为 Agent 节点运维，我希望在节点前面配置的上级代理对共享连接同样生效，以便部署方式不必改变。
10. 作为 Agent 节点运维，我希望运行时关闭或热重载移除时，它的共享连接全部释放，以便不留下悬挂连接。
11. 作为 Agent 节点运维，我希望一个回合被取消时只取消它自己的上游请求，不影响共用同一连接的其他回合。
12. 作为 Agent 节点运维，我希望上游的错误、限流响应头与错误文档照旧原样传给调用方，以便共享连接不改变现有的错误透传。
13. 作为 Agent 节点运维，我希望 Codex 运行时有少量预热好的 app-server 备用，以便请求不必等进程启动和初始化。
14. 作为 Agent 节点运维，我希望预热的 app-server 只用一次就销毁，以便请求之间的隔离与现在完全相同。
15. 作为 Agent 节点运维，我希望预热进程空闲太久就被回收并重新预热，以便它们不会带着过期的登录状态或旧的状态库种子。
16. 作为 Agent 节点运维，我希望预热进程的数量有明确且很小的默认值，以便它们占用的内存可预期（Codex 每个约 93–145 MB，Claude 约 222 MB）。
17. 作为 Agent 节点运维，我希望预热进程不占用运行时的并发名额，但也不能无限增长，以便它不会挤掉真实请求，也不会耗尽内存。
18. 作为 Agent 节点运维，我希望预热进程坏掉或拿不到时自动退回冷启动，以便预热永远不会让请求失败。
19. 作为 Agent 节点运维，我希望 Agent 关闭时连同预热进程一起回收整个进程组，以便不留下孤儿进程。
20. 作为 Agent 节点运维，我希望回合日志标明这一轮是否用了预热进程、是否复用了上游连接，以便对比两种路径的耗时。
21. 作为 Agent 节点运维，我希望 Claude 预热进程按路径分开（原生直通、带安全检查的原生回合）且按账户分开，以便一个请求永远不会拿到启动参数不匹配的进程。
22. 作为 Agent 节点运维，我希望 Claude 预热进程实际发给上游的请求，与冷启动时逐字节一致，以便预热不改变模型看到的内容和计费。
23. 作为 Agent 节点运维，我希望 Claude 的账户额度状态能从回合响应头里更新，以便少起专门查询额度的 CLI 进程。
24. 作为 Agent 节点运维，我希望只有 5 小时或 7 天窗口被拒绝时才冷却整个账户，以便超额或单个模型被拒不会误伤整个账户。
25. 作为调用方（经 Gateway 使用 Claude Code 的开发者），我希望首 token 更快，以便工具循环里每一轮都少等。
26. 作为调用方（经 Gateway 使用 Codex 的开发者），我希望长会话的提示缓存能命中，以便首 token 更快、输入费用更低。
27. 作为调用方，我希望这些优化不改变响应内容、停止原因、工具调用或用量统计，以便客户端行为与之前完全一致。
28. 作为调用方，我希望优化出错时请求照常成功（走冷启动路径），而不是新增 400 或 5xx 错误。
29. 作为平台运维，我希望能看到 Codex 多轮长会话的缓存读取占比，并能与 Claude 原生回合对照，以便判断缓存亲和性的改造是否值得立项。
30. 作为平台运维，我希望在有额度预算的前提下，能用一段固定的多轮对话分别经 Agent 和直连 Codex 跑一遍，逐轮比较缓存命中，以便证实或否定「每个请求都是新线程，缓存亲和性因此丢失」的推断。
31. 作为 Agent 节点运维，我希望 CLI 升级后能用离线基准重新测一遍冷启动，以便发现某个版本新增了阻塞启动的请求。
32. 作为 Agent 节点运维，我希望离线基准列出 CLI 在模型请求之前发出的请求，以便知道哪些请求在关键路径上。
33. 作为平台运维，我希望每项优化只需升级 Agent，不改隧道协议或 Gateway，以便可以逐个节点灰度。
34. 作为平台运维，我希望可以按运行时关掉某项优化，以便发现问题时不必回退整个 Agent。

## 实现决策

### 启用门槛与成功标准

门槛按部署后 1–3 天的线上分布判断，基线数字见「补充说明」：

| 优化项 | 依据的指标 | 启用门槛 | 成功标准 |
| --- | --- | --- | --- |
| Claude 同账户共享上游连接 | Claude 原生回合的 `cli_ready_ms` 减本机基线（约 172 ms） | p50 ≥ 100 ms | 该差值的 p50 下降不少于 200 ms（约一次握手；原定「下降至少一半」，2026-11-19 按实测握手与往返耗时修订，见 Comments），且回合不新增失败 |
| Codex 预热进程 | `history_injected_ms` | p50 ≥ 300 ms 或 p95 ≥ 1 s | 使用预热进程的回合，该值 p50 ≤ 50 ms |
| Claude 预热进程 | 共享连接上线后的 `request_sent_ms` | p50 ≥ 500 ms，且占 Agent 段（隧道首事件指标）≥ 30% | 使用预热进程的回合，`request_sent_ms` p50 下降至少一半 |
| Codex 缓存亲和性（只测量） | 输入超过 2 万 token 的请求，`input.cache_read / input` | 无（必做测量） | 出具按运行时种类的对比结论；命中率 < 30% 且明显低于 Claude 原生时，另立规格 |
| 用响应头更新 Claude 账户额度 | 每小时额度查询进程数 | 每节点每小时 ≥ 60 个 | 额度查询进程数下降至少一半，额度显示与搁置判断不变 |

### Claude 同账户共享上游连接

- **改动范围**：Claude 运行时的每进程上游代理。
- **连接按运行时共享**：每个运行时（一个账户目录）持有一个到上游的连接池，该运行时所有回合的每进程代理共用它，并允许 HTTP/2 多路复用。不同运行时之间从不共用；同一台机器上的多个账户各有各的池。
- **每进程代理其余部分保持独立**：临时 CA、回环监听、访问口令、截获记录、主请求的文档合并与错误透传都和现在一样。只有「到上游的连接」改为共享。
- **只共享解密后的 api.anthropic.com 请求**：对其他主机的 CONNECT 隧道照旧每次单独建立，不共享。
- **上级代理**：路由按该运行时的环境变量决定，与现在一致；共享池对经上级代理的连接同样生效。
- **取消**：单个回合结束或被取消时，通过请求上下文取消它自己的上游请求，不再关闭连接。每进程代理关闭时，不得关闭共享池里的连接。
- **释放**：运行时关闭或被热重载移除时，释放它的共享池和全部连接；空闲连接按超时回收。
- **观测**：回合日志的 `upstream_conn_reused` 与 `agent_cli_upstream_connect_seconds{reused}` 继续可用。成功的话，`cli_ready_ms` 会下降，因为启动请求也开始复用连接。
- **开关**：可以按运行时关闭，关闭后回到每进程独立连接；开关只能在本地配置，不接受 Gateway 下发。

### Codex 预热进程

- **改动范围**：Codex 运行时的进程管理。
- **预热到哪一步**：每个运行时维持少量备用 app-server，默认 1 个。备用进程已完成状态库种子复制、启动、`initialize` 与 `account/read`，停在 `thread/start` 之前。
- **只用一次**：请求取走一个备用进程，用完照旧销毁；取走后在后台补一个新的。请求之间的隔离、临时目录与 ephemeral 线程都不变。
- **空闲回收**：备用进程空闲超过固定时长（默认 60 秒）就回收重建，避免带着过期的登录状态或旧种子。回收用运行时注入的时钟计时。
- **数量与并发名额**：备用进程不计入 `max_concurrent`，但数量有上限，按运行时配置，默认 1。
- **失败退回冷启动**：备用进程已经退出、协议出错或取不到时，静默改走冷启动，不让请求失败。
- **关闭**：运行时关闭与 Agent 关闭时，回收全部备用进程组。
- **范围**：健康检查、模型目录、额度查询与生图进程不使用备用进程。
- **观测**：回合日志与阶段指标标明是否为预热启动（例如 `warm_start` 字段与对应的指标标签），以便分开统计。
- **开关**：按运行时本地配置，可关闭。

### Claude 预热进程（先做原型）

- **原型要回答的问题**：
  - CLI 能否在收到请求内容之前启动，并完成组织策略、远程设置与功能开关这几个启动请求？例如以流式 JSON 输入启动并等待 stdin。
  - 上游实际收到的模型请求，能否完全由每进程代理在请求到来时注入的文档决定？包括模型、消息、系统提示、beta 选择与 API 版本。
- **约束**：只用官方文档记载的 CLI 行为。不依赖 Agent SDK 的 alpha 预热协议（`--await-claim` / `claim_session`），除非原型证明没有别的办法，而且要单独决策。
- **预热池分开**：按账户、按路径（原生直通与带安全检查的原生回合启动参数不同）各自独立。只用一次、空闲回收与失败退回冷启动的规则与 Codex 相同。
- **验收**：同一请求经预热进程与冷启动进程，回环上游收到的模型请求逐字节一致。

### Codex 缓存亲和性（只测量）

- 从用量记录按运行时种类汇总 `input.cache_read / input`，只看输入超过 2 万 token 的请求，与 Claude 原生回合对照。
- 可选的对照实验会消耗额度，须先取得同意：同一段固定的 8 轮对话，分别经 Agent 和直连 Codex 运行，逐轮比较 `cachedInputTokens`。
- 结论写回本规格。需要改造时另立规格。已知 app-server 没有暴露提示缓存 key 的覆盖方式，改造很可能意味着按会话保留线程。

### 用响应头更新 Claude 账户额度

- 每进程代理在主请求上已经截获了 `anthropic-ratelimit-unified-*` 响应头，用它们更新该运行时的账户额度状态（窗口用量与重置时间）。
- 分类规则参考 CLIProxyAPI：只有 5 小时或 7 天窗口为 rejected 时才冷却整个账户；超额或单个模型被拒不冷却整个账户。
- 有新鲜的响应头数据时，延长专门查询额度的间隔；没有回合流量时照旧定期查询。
- 设置页面与隧道上报的额度格式不变。

### 通用约束

- 只改 Agent；隧道协议、Gateway 与控制面都不变，可以逐节点升级。
- 所有优化都不能新增请求失败的路径：优化本身出错时退回现有路径。
- 日志与指标只记录耗时、计数和固定分类，不记录请求内容。
- 每项优化的开关都只能在本地配置，不接受 Gateway 下发，与现有的本机 CLI 运行时边界一致。

## 测试决策

- **好测试的标准**：只通过运行时的公开入口验证外部可见的行为（回合结果、回环上游实际收到的连接与请求、回合日志字段、指标），不对内部结构的状态做断言。
- **Claude 共享连接**：经运行时的 Messages 入口跑真实子进程，用假 CLI 或已安装的 CLI，对着现有的「本机冒充 api.anthropic.com」回环上游。覆盖：
  - 同一运行时连续两个回合，回环上游只接受一条新连接；第二个回合的日志里 `upstream_conn_reused` 为 true。
  - 两个不同运行时（不同账户目录），各自建立自己的连接。
  - 一个回合被取消，同时进行、共用连接的另一个回合仍能完成。
  - 运行时关闭后，回环上游看到连接全部关闭。
  - 上游返回 429/529 时，响应头和错误文档仍原样透传。
  - 关闭开关后，回到每回合新建连接。
- **Codex 预热进程**：经运行时的 Chat/ChatStream 入口跑现有的假 app-server 子进程。覆盖：
  - 假进程记录自己的启动时刻与次数：请求到来之前备用进程已经启动，请求用完后后台补起一个新的。
  - 用注入时钟推进空闲时长，备用进程被回收并重建。
  - 备用进程启动后立即退出，或协议出错时，请求改走冷启动并照常成功。
  - 运行时关闭后不留进程，由包内现有的协程回收检查兜底。
  - 健康检查、模型目录与生图不使用备用进程。
  - 回合日志标明是否为预热启动。
- **Claude 预热原型**：用回环上游比较预热路径与冷启动路径收到的模型请求是否逐字节一致；这一条也是将来实施时的回归测试。
- **效果量化**：用已有的 `TestCLIStartupBenchmark`（`AISW_CLI_BENCH=1`）与线上 `agent_cli_*` 指标，不新增接缝。基准扩展为分别报告冷启动与预热两条路径。
- **已有的测试可以参考**：
  - Claude：大请求契约测试的回环上游（本机冒充 api.anthropic.com）、原生回合计时测试、safeguards 运行时测试。
  - Codex：运行时生命周期测试与假 app-server 夹具、回合计时测试、并发限额与关闭测试。
  - 基准：两个包的 `TestCLIStartupBenchmark`。
- **回归**：现有的隔离、取消、优雅终止、失败分类与错误透传测试都必须继续通过；改动的包要跑竞态检查与 Windows/Linux 交叉编译。

## 不在范围内

- 按会话保留 Codex 线程以恢复提示缓存亲和性的改造（视测量结论另立规格）。
- 让一个常驻 CLI 或 app-server 进程同时服务多个请求或多个租户。
- 在每进程代理里缓存 Claude 的启动请求答复（组织策略、远程设置、功能开关）。这会改变策略生效的及时性，需要单独决策，见「补充说明」。（2026-11-27 已决定纳入并实施，见 Comments「启动请求缓存」。）
- 关闭遥测与功能开关拉取（`DISABLE_TELEMETRY`、`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`）。safeguards 路径须先在真实主机上复验。
- 可配置的 CLI 可执行文件路径（固定 CLI 版本的后续项）。
- 用真实账户复验 Codex 新关闭的宿主工具（`TestLiveCallerToolRoundTrip`）。
- Codex `optOutNotificationMethods` 降噪；只有 profiling 显示 Agent CPU 是瓶颈时才考虑。
- 绕过 CLI 直连 ChatGPT 或 Anthropic 的私有后端。
- fast mode、优先级或任何加急类服务等级。
- 新增请求上限或更严格的校验。用户明确要求：稳定性与性能改进不靠新增限制，限制会造成 400/5xx。

## 补充说明

**本机基线**：2026-11-18，macOS arm64 开发机，回环、无网络往返，各 20 次，p50 / p95：

| | 到能发出模型请求或接收回合 | 每回合 CPU | 峰值内存 |
| --- | --- | --- | --- |
| Claude Code 2.1.327 原生回合 | `request_sent` 188 / 463 ms | 266 ms | 约 222 MB |
| codex-cli 0.169.0，256 KB 历史 | `history_injected` 59 / 203 ms | 67 ms | 约 93 MB |
| 同上，带入 44 MB 会话历史 | 160 / 213 ms | 111 ms | 约 97 MB |
| 同上，4 MiB 历史 | 116 / 170 ms | 146 ms | 约 142 MB |

**Claude 启动请求**：离线基准显示，每个回合在模型请求之前，CLI 会请求 `GET /api/claude_code/policy_limits`、`GET /api/claude_code/settings` 和功能开关 `POST /api/eval/sdk-…`（各 1 次），以及 `GET /api/claude_cli/bootstrap` 和 `GET /api/claude_code_penguin_mode`（约三分之一的回合）。CLI 要等组织策略与远程设置答复后才开始；答复读不懂或上游不可达时，会按退避重试约 18 秒。每进程代理在这些请求上已经建好连接，所以模型请求的 `upstream_connect_ms` 通常为 0，每个进程新建连接的成本算在 `cli_ready_ms` 里。

**启动请求缓存（未纳入本期）**：每进程代理可以按账户、用很短的有效期缓存组织策略与远程设置的成功答复，这能直接省掉每个回合的几次往返。但它会让组织策略的变更最多晚一个有效期才生效，而功能开关请求可能带有会话属性，所以要单独评估和决策。

**外部参考**：
- Claude Agent SDK 的 `startup()` 与 alpha `prewarm()`：备用进程以 `--await-claim` 启动，同一套参数下只能使用一次。
- Codex 官方 Python SDK：一个常驻 app-server 服务多个回合；`-32001` 表示过载，退避后重试。
- CLIProxyAPI 对 Claude 额度响应头的分类规则。

**用户偏好**：改进不靠新增限制。任何优化都必须在出错时退回原路径，不新增 400、5xx 或挂起。

**升级**：只需升级 Agent。

### 2026-11-27 启动请求缓存（已实施）

- 用户决定纳入（原列在「不在范围内」）：命中即答并后台刷新，超过 10 分钟未刷新成功的答复不用；功能开关请求缓存，键里去掉 `attributes.sessionId`；`policy_limits` 不理会其 `Cache-Control: no-cache`。
- 离线探测更正「补充说明」：CLI 2.1.330（API key 登录）只有 `policy_limits` 与功能开关求值阻塞模型请求，二者先后发出；`settings`、`bootstrap`、`penguin_mode` 不阻塞。各给上游加 300 ms 延迟时，到模型请求发出分别增加约 360 ms 和 340 ms，两者都加约 600 ms。
- 本机回环加 300 ms 延迟：到模型请求发出约 890 ms → 第 2 回合起约 200 ms（每回合命中 2 次）。生产用 OAuth 登录，请求集合可能不同，部署后看 `startup_cache_hits` 与 `request_sent_ms` 复测。
- 2026-11-28 部署到 Mac mini（OAuth 登录，CLI 2.1.332）：上线后前 7 个回合 `startup_cache_hits` 都是 1，不是 2。带安全检查回合的 `request_sent_ms` 从 p50 1402（11-27 的 400 个回合）降到约 1100，样本太少。该机 `~/.claude.json` 的功能开关缓存里没有 `tengu_gb_eval_authed_enable`，CLI 发的仍是 `/api/eval/`。本机用假 OAuth token 回环跑 4 轮，每轮命中 2 次，复现不了。已新增 `startup_cache_misses` 记录未命中原因，再次部署后据此定位。
- 2026-11-28 再次部署（带 `startup_cache_misses`）后 72 个回合：`startup_cache_hits` 全为 1，未命中只有重启后的一次 `eval:first`，`policy_limits` 从未出现。结论：该 OAuth 账户的 CLI 不发 `policy_limits`，每回合唯一需要等待且可缓存的是功能开关求值，已全部命中。对比 11-27 的 400 个回合：带安全检查 `request_sent_ms` p50 1402 → 1080 ms、p90 1960 → 1224 ms（58 个回合），`request_sent − cli_ready` 从约 480 ms 降到约 140 ms；原生直通 16 个回合 p50 1409 → 1455 ms，其中 `cli_ready` 升高 255 ms 抵消了收益，样本太少，待更多回合后复看。
