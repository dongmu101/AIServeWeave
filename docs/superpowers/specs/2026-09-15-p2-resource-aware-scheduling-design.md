# P2-1 GPU/系统资源采集、资源感知调度与有界任务排队

本文档交付根 STATUS.md「P2：后续扩展」第五条：GPU/显存和系统资源采集、资源感知调度，以及有界任务排队；已提交的 ComfyUI 任务不自动跨节点迁移。M4 里程碑对 P2 全部条目的统一要求是「各项先明确场景、依赖与验收，再拆分实施；不以功能数量代替稳定性门槛」（STATUS.md:19），本文档据此执行。

范围边界：**本项以设计文档为主，不含新代码或新测试**，与 [A01](2026-09-14-a01-scope-reliability-design.md)、[A04](2026-09-15-a04-direct-mode-boundary-design.md)、[A05](2026-09-15-a05-scheduling-extension-breakdown-design.md) 同一先例。A05 第 1.6 节已经核实过同一处代码缺口（静态硬件清单 vs 实时利用率），第八节第 5 条明确写着「与 STATUS.md P2 待办重复记录同一缺口……但两者是独立任务，不应合并排期」——本文档就是那项独立任务，不重复 A05 已完成的核实，只在必要处引用其结论，聚焦 P2 措辞里 A05 未覆盖的两块：**采集怎么做到**（A05 只确认了"未采集"，未评估采集手段）与**有界任务排队**（A05 完全未涉及）。凡属阅读代码得出的结论标注文件:行号；仅在文档散文中出现、找不到代码依据的计入第八节缺口清单。

## 一、现状盘点

### 1.1 NodeResources 是结构性缺失，不是零值

`tunnelv1.Hello.Resources` 由 Agent 的 `Config.Resources *tunnelv1.NodeResources` 直接透传（`service/aiServeWeaveAgent/tunnel/client.go:452`），该配置字段的注释明确写着"may be nil"（`client.go:171-173`）。全仓库范围内唯一给它赋值的地方是测试代码（`client_test.go:250`：`cfg.Resources = &tunnelv1.NodeResources{CpuCores: 10, GpuCount: 1, Os: "darwin"}`），Agent 的 `main.go` 与配置加载路径都不填充这个字段。全仓库没有任何 OS/GPU 探测依赖（`gopsutil`/`nvml`/`ghw` 等关键字零命中，`go.mod` 无此类依赖）。因此 `renderNode` 里的 `if res := info.Resources; res != nil`（`service/aiServeWeaveGateway/adminapi/adminapi.go:231`）在生产环境从未为真——不是"字段存在但是空硬件清单"，而是这个指针今天永远是 `nil`。`common/nodeview.Resources`（`nodeview.go:126-136`）作为对 Console 的允许列表镜像，同样因此从未渲染出真实数据。

### 1.2 调度器完全不读取硬件容量，也不读取任何占用信号

`Scheduler.pickBy`（`service/aiServeWeaveGateway/scheduler/scheduler.go:397-451`）遍历候选节点时只使用四类信号：`target.MatchesNode(node.Labels)`（标签路由）、`node.IdleSlots[SLOT_CLASS_INFERENCE]`（空闲槽）、`node.InflightRequests`（在途请求）、以及熔断器状态；排序键是 `idle` 降序、`inflight` 升序。`node.Resources`（无论是否为 nil）从未出现在 `scheduler.go` 里，`common/modelroute` 也没有任何字段引用 `GpuCount`/`GpuMemoryBytes`/`CpuCores`。也就是说，即便 1.1 节的缺口被补上、`NodeResources` 真正携带了硬件容量，今天的调度路径也不会消费它——这是两处独立的缺口，缺一不可。

### 1.3 心跳协议不携带任何"实时利用率"信号

`Heartbeat` 消息（`api/proto/tunnel/v1/tunnel.pb.go:2643-2650`）只有 `SentUnixMs`/`InflightRequests`/`IdleSlots` 三个字段。`common/runtime.HealthReport`（`common/runtime/types.go:74-82`）只有 `State`/`Latency`/`CheckedAt`/`ErrorSummary`，没有内存/显存占用字段。ComfyUI 适配器新增的队列指标（`common/runtime/workflow/comfyui/metrics.go`，A06 交付）反映的是**该后端自己的作业队列深度**（`GET /queue` 的 running/pending），不是显存占用——一个队列很浅但每个任务都吃满显存的节点，和一个队列很深但任务都很轻的节点，在现有信号下无法区分。全仓库没有任何路径回答"这台节点此刻还剩多少可用显存/内存"。

### 1.4 有界任务排队：今天的准入模型是"拒绝换节点"，没有排队这个概念

有两层容量控制，都不是队列：

1. **每 runtime 的硬并发上限**：`common/runtime.Config.MaxConcurrent`（默认 32，`common/runtime/config.go:18,60-62`）通过 `runtime.NewLimiter` 接入各适配器（`oaibase.go:100`、`comfyui/runtime.go:127`），超限时以 `ErrorBackpressure` 拒绝（`common/runtime/errors.go:32`：该错误码的注释明确"Agent 自己拒绝发送"，区别于后端说 no 的 `ErrorRateLimited`/`ErrorUpstream`）。
2. **Agent 侧槽池是软配额**：`node.acquire`（`service/aiServeWeaveGateway/tunnelserver/node.go:317-320`）的文档注释是本节最关键的一句现状证据——"It never blocks and never queues: an empty idle set is backpressure, and the answer to backpressure is another node, not a wait"（它从不阻塞也从不排队：空的空闲集就是背压，背压的答案是换一个节点，不是等待）。

`scheduler` 的 `Retry` 计数器（`scheduler/metrics.go:176`，被 `workflow.go`/`scheduler.go` 调用）印证了同一模型：一个候选给出 `ErrorBackpressure` 后，调度器切换到候选列表里的下一个，从不让请求在原地等待。这意味着 STATUS.md 措辞里的"有界任务排队"如果要实现，是一个**全新机制**，不是对现有机制的参数化扩展——今天连"无界排队"都不存在，只有"立即拒绝、换节点重试"。

### 1.5 "已提交的 ComfyUI 任务不自动跨节点迁移"是对既有事实的重申，不是新设计点

工作流 Job 提交后绑定固定的执行位置（节点/运行时），后续的状态轮询、取消、产物访问都打到同一个绑定（AGENTS.md 代码地图「`common/workflowview`」一行："job 不含运行位置（节点/运行时/解析后的模型）……是刻意的"是契约层面的描述；实际绑定落在 Gateway 的 job 状态与路由持久化里）。STATUS.md 这句话是在澄清"资源感知调度只影响*新提交*任务选哪个节点，不隐含对已在跑的任务做迁移"，本文档据此确认：**跨节点迁移不在本项及任何后续拆分任务的范围内**，无需单独设计。

## 二、场景与目标定义

把 STATUS.md 一句话拆成三个独立且颗粒度不同的问题，避免像 A05 第 1.6 节警告的那样把"静态容量"和"实时利用率"混为一谈：

1. **准入门槛（容量层面）**：一个大模型工作流不应该被派给显存总量明显不够的节点，即便该节点当前空闲槽最多。这只需要 1.1 节的静态 `NodeResources` 被真正填充，属于"硬件清单存在与否"的问题，不涉及实时占用。
2. **负载感知排序（占用层面）**：在多个容量都够用的候选之间，优先选当前显存/内存压力更小的一个。这需要 1.3 节指出的、今天完全不存在的实时利用率信号，比准入门槛难得多。
3. **有界排队（背压层面）**：当所有候选都因容量或占用被排除时，今天的行为是让请求立即失败（或由客户端重试整个请求），STATUS.md 希望引入一个有界等待窗口，而不是无界排队（AGENTS.md 安全红线："任何一跳都不得无界缓冲"对此同样适用）。

这三者可以独立交付：场景 1 不依赖场景 2、3；场景 3 甚至不依赖场景 1、2（一个纯粹基于 idle/inflight 的有界队列同样有意义）。第七节据此拆分任务。

## 三、依赖与红线

1. **Agent 依赖红线是本项最大的实现约束。** AGENTS.md 明确写着"Agent 与 Registry 的直接依赖只有 gRPC、protobuf 与 `coder/websocket`，这条线要守住"。GPU/系统资源探测的常见手段——`gopsutil`（跨平台 CPU/内存，GPU 支持有限）、NVML 的 cgo binding（Linux NVIDIA 精确显存）——都是需要说明理由的新依赖，直接违反这条红线，除非走 Gateway 的 `go-redis` 那种"经评估的例外"路径。**相反，用标准库 `os/exec` shell out 到平台自带工具**（Linux/NVIDIA 的 `nvidia-smi --query-gpu=... --format=csv`、macOS 的 `system_profiler SPDisplaysDataType` 或 `vm_stat`/`sysctl`、CPU 核数与内存可直接用 `runtime.NumCPU()`/`golang.org/x/sys` 之外的标准库手段）不引入任何 Go 依赖，与红线的精神完全一致，应作为默认候选。
2. **跨平台覆盖不完整是已知且无法在设计阶段解决的缺口。** 参考部署本身是 macOS 开发环境（README 已多次提及），macOS 上不存在等价于 `nvidia-smi` 的通用 NVIDIA 显存查询工具（Apple Silicon 走 Metal，没有独立显存概念）；Linux+NVIDIA 是唯一有可靠 shell-out 手段的组合，AMD ROCm（`rocm-smi`）需要单独适配。采集实现必须做成"探测不到就留空，不阻塞、不报错"，而不是假设某个工具一定存在。
3. **探测过程不能成为新的攻击面或阻塞点。** shell out 的命令行必须是硬编码的固定命令+参数，不能拼接任何外部输入（避免命令注入）；探测必须有超时并在独立 goroutine/周期任务里跑，不能挤占心跳发送路径——AGENTS.md 安全红线"任何一跳都不得无界缓冲"同样要求探测失败或挂起不能拖慢 `Heartbeat`。
4. **`NodeResources` 复用现有 proto 字段，不需要 proto 改动**（前提是只交付静态容量，场景 1）；场景 2 需要的实时利用率若要走 `Heartbeat`，需要给 `tunnel.proto` 新增字段并重新生成（走 AGENTS.md「契约唯一源」流程），这是一处需要在实现阶段评估的协议改动，也应参照 A03 设计文档已给出的 proto 演进规则（新增字段对旧读者安全）。

## 四、采集实现候选方案

| 方案 | 覆盖范围 | 是否新增依赖 | 评估 |
| --- | --- | --- | --- |
| `os/exec` shell out 平台工具 | Linux+NVIDIA 完整；macOS 仅 CPU/内存，无 GPU；AMD 需另接 `rocm-smi` | 无 | 与依赖红线精神一致，推荐作为默认实现路径 |
| `gopsutil` | CPU/内存跨平台良好，GPU 支持薄弱（无官方 GPU 模块） | 是，需评估例外 | 只解决 CPU/内存，GPU 仍需 shell out，等于两套机制并存，收益有限 |
| NVML cgo binding | Linux+NVIDIA 精确（显存实时占用而非总量） | 是，cgo + 平台限定，需评估例外 | 精度最高但违反红线最明显，且 cgo 会打破 Agent 当前纯 Go 交叉编译的部署简单性，只应在 shell out 方案证明精度不足时才考虑 |

建议：CPU 核数与内存总量用标准库（`runtime.NumCPU()`；内存总量本身跨平台也没有标准库直接接口，仍需 shell out 或读 `/proc/meminfo`），GPU 计数与显存用 `nvidia-smi` shell out（Linux）、macOS 上留空。这组合覆盖 STATUS.md 场景 1（准入门槛）所需的静态容量，且不新增依赖。

## 五、数据形状与调度消费方式候选

1. **静态容量（场景 1）复用现有 `NodeResources`，不需要新结构。** 只需要 Agent 侧真正填充 `Config.Resources`（第一节 1.1 的缺口），Gateway 侧 `pickBy` 新增一次容量过滤：候选节点若声明了 `GpuMemoryBytes` 且目标 target/model 有已知的显存需求，容量不足则排除该候选。这里立刻出现一个新问题——**模型的显存需求从哪来**，今天 `modelroute.Target`/`routing.Target` 没有任何"这个模型大约需要多少显存"的字段，这是场景 1 的前置缺口，需要单独定义（类比场景 2 缺流水线信号、场景 2 之外还缺模型侧的需求声明）。
2. **实时利用率（场景 2）需要新的 Heartbeat 字段或独立的资源上报通道**，且需要决定更新频率——心跳间隔（`defaultHealthInterval` 量级，`common/runtime/config.go:16`）是否足够及时，还是需要独立于心跳的采样频率，这直接影响 Agent 端探测开销（shell out 是相对重的操作，不宜每次心跳都执行）。
3. **调度消费方式建议分两步接入 `pickBy`**，与 A05 第四节第 1 条"先用已有信号做低成本实现、再评估精确方案"的方法论一致：先做**过滤**（容量不足直接排除，不参与排序，逻辑简单、可解释性强），再评估是否需要把利用率接入**排序**（会引入"利用率精确度不够导致误排序"的新风险，A05 已经在延迟评分上警告过这类偏差）。不建议一步到位把利用率做成排序权重，避免像成本评分那样"发明一个看似有依据实则是噪声的分数"（A05 第四节第 2 条的告诫同样适用于精度不明的资源信号）。

## 六、有界任务排队设计草案

1. **排队应该是每节点/每 runtime 的等待窗口，而不是 Gateway 全局队列。** 现有背压发生在具体的 `NodeRuntime`/slot 层面（`node.acquire` 返回 nil），有界排队最自然的落点是在"所有候选都暂时不可用"时，允许请求在**候选集合**层面等待一个有界的时间窗口（例如几秒），而不是在某一个节点上排队——这样能保留现有"换节点重试"的优势，只是把"立即失败"改成"短暂等待后再试一轮候选遍历"。
2. **必须有严格的上界，且上界要对调用方可见。** 有界排队违反 AGENTS.md 安全红线的风险点在于"无界缓冲"——设计必须包含：(a) 最大等待时长（超时后按今天的行为立即失败）；(b) 最大排队请求数（超过则直接拒绝，不接受新的等待者），这两个上界都应可配置而非硬编码，且需要指标可观测（复用 `scheduler/metrics.go` 现有的 `recorder` 模式新增一个排队深度/排队时长的量表）。
3. **只对工作流 Job 合理，OpenAI 前门的同步请求需要单独评估。** Chat/Embed 是同步 HTTP 请求，客户端已经在等待响应，让它在 Gateway 内部再排队会直接叠加到客户端的请求超时上，且与 README.md 已有的"流式响应首 token 前才可重试"规则（A05 第五节第 3 条已引用）存在交互——排队时间过长会让客户端自己的超时先触发，排队变得没有意义。工作流 Job 是异步提交+轮询模型（`httpapi/jobstore.go`），天然更适合排队：提交时可以立即接受，进入内部等待窗口，若窗口内等不到容量再转入失败终态，这个语义比同步请求排队更清晰。**因此第一版有界排队应只覆盖工作流 Job，不覆盖 Chat/Embed**，这也与 STATUS.md 原句"已提交的 ComfyUI 任务不自动跨节点迁移"把讨论范围锚定在工作流场景一致。
4. **排队与准入门槛（场景 1）的交互需要明确顺序。** 容量明显不够的节点应该在候选阶段就被排除，不应该进入排队等待——排队解决的是"容量足够但暂时都忙"，不是"永远不会有节点能满足"，后者排队到超时也不会有结果，属于应该立即拒绝的情形。

## 七、验收目标（供未来实现该功能时使用；本项不实现）

1. Agent 新增的资源探测（shell out 方案）有测试覆盖：探测工具不存在时不报错、不阻塞、`NodeResources` 对应字段留空；探测超时不拖慢心跳发送节奏。
2. `pickBy` 新增的容量过滤有测试覆盖：候选声明的 `GpuMemoryBytes` 不足以满足目标模型的显存需求时被排除，未声明资源信息（`Resources == nil`）的候选保持现有行为不变（向后兼容，不能因为这项功能上线就让今天未上报资源的节点全部失去候选资格）。
3. 有界排队有测试覆盖：候选集合暂时为空时请求在配置的等待窗口内重试候选遍历；超过最大等待时长或最大排队请求数后按今天的行为立即失败；排队深度/等待时长有指标可观测。
4. 有界排队的范围限定在工作流 Job 提交路径，Chat/Embed 端点行为不变，需要显式测试证明未受影响。
5. STATUS.md P2 该条随每一项实际交付更新状态标注，不在功能完成前提前标注为已实现。

## 八、后续实现任务的拆分建议（不在本文档范围内交付）

1. **静态资源采集（Agent 侧）**：实现 `os/exec` shell out 探测并填充 `Config.Resources`（第四节），是任务 2、3 的前置依赖，可独立交付且改动面小（只涉及 Agent 与其测试）。
2. **准入门槛过滤（Gateway 侧）**：`pickBy` 新增容量过滤（第五节第 1、3 条），依赖任务 1 提供真实数据，且需要先解决"模型显存需求从哪来"这个前置缺口——这本身可能是一个独立的子任务（例如在 `modelroute.Target` 或模型元数据里新增一个可选的资源需求声明）。
3. **实时利用率采集与协议扩展**：评估是否需要新的 Heartbeat 字段或独立上报通道（第五节第 2 条），依赖 AGENTS.md 契约唯一源流程（proto 改动 + 重新生成），且需要先证明静态过滤（任务 2）不足以满足场景后再排期，避免过度设计。
4. **有界任务排队（工作流 Job）**：候选集合层面的等待窗口 + 上界 + 指标（第六节），可与任务 2 并行设计，因为排队解决的是"容量足够但都忙"，与"容量本身不够"是两个独立问题；但排队与过滤的交互顺序（第六节第 4 条）需要在两者都设计完成后统一验收。

任务 1 是任务 2、3 的硬前置；任务 4 除了第六节第 4 条提到的交互顺序外，与任务 1-3 相对独立，可并行推进。不建议把这四项合并成一次实现——与 A05 第七节"不建议按 STATUS.md 一贯的'一个编号对应一次可验收实现'的粒度把大项拆成一个任务"的先例一致。

## 九、已知缺口清单

1. **模型显存需求声明不存在**（第五节第 1 条）——准入门槛过滤若要有意义，必须先有"这个模型大约需要多少显存"的数据来源，本文档未给出该来源的具体设计，留给任务 2 实现阶段解决。
2. **实时利用率的更新频率与采集开销之间的取舍未定**（第五节第 2 条）——shell out 探测的开销是否允许按心跳频率执行，需要实测数据支撑，本文档只给出问题本身。
