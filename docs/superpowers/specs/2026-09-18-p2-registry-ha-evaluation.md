# Registry 高可用评估

本文档交付根 STATUS.md「P2：后续扩展」的一项，出自"Agent 自动升级、Kubernetes 部署、Registry 高可用"这一条目——上次会话已核实前两者在代码里完全不存在且各自是独立工程（STATUS.md:124），本文档单独评估第三者：Registry 高可用。

范围边界：**本项以评估与方向选型为主，不含新代码或新测试**，与 [A04](2026-09-15-a04-direct-mode-boundary-design.md)/[A05](2026-09-15-a05-scheduling-extension-breakdown-design.md)/[Tunnel Gateway 评估](2026-09-18-p2-tunnel-gateway-event-infra-evaluation.md) 同一先例。原因更进一步：Registry README 自己已经把"单实例假设"列为已知限制（README:159），要把它变成一个可运行的多活方案，需要先解决第三节指出的一处真实设计张力（CA 私钥的"单进程持有"声明与"高可用"字面要求的私钥可用性互相冲突），这个张力目前没有仓库既有代码或文档给出答案，选哪个方向本身就是需要独立记录、可能需要运维/安全侧确认的架构决策，不是可以在核实过程中顺手定下来的细节。凡属阅读代码得出的结论标注文件:行号；仅在 README/STATUS 散文中出现、找不到代码依据的一律计入第七节缺口清单。

## 一、"高可用"先要拆开:今天已经有的韧性,和真正缺的东西不是一回事

STATUS.md 与 Registry README 都只说"单实例假设"/"高可用",没有定义这具体指什么。核实现状后,"高可用"实际上包含三件互相独立、成熟度完全不同的事,必须先拆开讨论,否则容易把"已经够用的部分"也一起重做:

1. **已建立连接的韧性——已经很强,不需要 HA 就成立。** [A01](2026-09-14-a01-scope-reliability-design.md) §3.4 已核实:Agent↔Gateway 的 mTLS 隧道一旦建立,不依赖 Registry 持续在线,证书 30 天有效期给了远超一次运维故障处理时长的容忍窗口。Registry 完全下线,不会让任何一个已经连上的节点掉线。
2. **单进程的故障恢复(重启)——已有真实验证数据,但不是"高可用"。** [A02](2026-09-14-a02-disaster-recovery-key-rotation-design.md) 对 Registry 做过一次真实(非合成)的备份恢复演练,观测到单容器重启 RTO 约 3 秒,并发现一个此前未记录的行为:只删磁盘文件不重启进程不构成数据丢失(内存态在下次写操作时自愈),真正的 RPO 边界是"进程重启"而非"文件损坏那一刻"。这证明了"一个 Registry 进程挂了,几秒内换一个新进程接着跑"这件事本身没问题——但这是"进程可重启",不是"服务不中断"。今天没有第二个 Registry 进程能在第一个还没重启完的几秒钟里接住流量。
3. **真正缺的:多个 Registry 进程同时在线时的强一致性——这是"高可用"字面要求的东西,目前完全没有设计。** 本文档的核实与评估集中在这一件事上。

**结论:如果"高可用"的目标只是"缩短运维发现故障到重启完成之间的几秒到几分钟",现状(单进程 + 自动重启/编排 + 已验证的备份恢复)已经基本满足,不需要新架构。** 只有当目标明确是"故障期间零停机,新节点注册/续期/吊销在任意时刻都不因单个 Registry 进程故障而阻塞"时,才需要第二至六节讨论的多活方案——第四节会说明为什么这条更高的门槛,在没有真实规模证据支撑时,成本收益不成立。

## 二、现状核实:单实例假设具体体现在哪三处代码里

Registry README 已经点出"单实例假设"(README:159),核实结果是这个假设精确对应三处独立的强一致性状态,单进程 `sync.Mutex` + 本地 JSON 文件是它们唯一的一致性保证:

1. **`tokenstore.Store`(`internal/tokenstore/tokenstore.go`)——bootstrap token 的一次性消费。** `Consume(token, now)` 在持有 `s.mu` 的临界区内检查 `Used`/`Revoked`/`ExpiresAt` 并原子地标记为已用(`tokenstore.go:160-181`,上次会话已核实行号)。`record.Token` 本身是 map 的键(`tokenstore.go:33-46`),意味着这个文件里存的是**明文的一次性凭据本身**,不是哈希——`fileMode = 0o600` 的注释直接写着"a bootstrap token is a bearer credential until it is consumed"(`tokenstore.go:70-72`)。两个进程各自拿着自己的内存态和文件副本,同一枚 token 能被两边都判定为"尚未使用"并同时放行——这正是"一次性"这个安全属性在多进程下失效的具体方式。
2. **`identitystore.Store`(`internal/identitystore/identitystore.go`)——`node_id` 指纹账本与禁用/待审批/维护标记。** `Reserve` 在 `s.mu` 临界区内比较并写入(`identitystore.go:184-219`),文档注释明确写着它存在的意义就是防止"两个并发的 `Register` 调用……不会让账本产生一次看到了旧值的竞态"(README:136)。两个独立进程各自持有的内存态互不可见,这条互斥保证在多进程下同样不成立——两个进程可能同时把同一个 `node_id` 的不同公钥都判定为 `OutcomeNew` 而放行,这正是 S01 这套机制本来要防的"身份冒用与合法重装分不清"。
3. **`ca.CA`(`internal/ca/ca.go`)——根私钥。** 包文档注释明确写着"the CA private key is the one piece of the system that must stay confined to a single process"(`ca.go:1-6`),对应 Registry README 顶部的设计声明"这两件事都要求强一致的一次性状态……所以只由 Registry 一个进程持有,不下发给任何 Gateway 副本"(README:3)。这条声明字面上是在对比 Registry 和 Gateway(私钥不下发给 Gateway),但它同时也是当前唯一一份持有私钥的进程——**这是第三节要展开的核心张力**。

`main.go` 的装配(`main.go:110-181`,上次会话已读)进一步证实:`ca.LoadOrCreate`、`tokenstore.Open`、`identitystore.Open` 都是本地文件路径,没有任何 flag 或代码路径指向共享存储、外部锁服务或集群协调。

## 三、核心张力:CA 私钥"单进程持有"与"高可用"字面要求互相冲突

**"高可用"意味着故障时另一个进程能立刻接管签发能力,这要求私钥在那个时刻对第二个进程可用——但现状的安全设计明确说私钥只应存在于一个进程。** 这不是一个可以靠更好的代码绕开的实现细节,是两个目标的直接冲突,后续任何方案都要在这条冲突上选边:

- **选择保留"单进程持有"不动摇**:那么"高可用"就不能是"任意时刻有第二个进程能签发",只能是第一节第 2 点已经有的"故障后快速重启/编排",这与"高可用"这个词通常的含义(多活、零停机)有落差,但对齐现状的安全设计和 [A01](2026-09-14-a01-scope-reliability-design.md) 已给出的、证书 30 天容忍窗口撑住的真实约束。
- **选择放宽"单进程持有",让私钥在故障时对备用进程可用**:意味着私钥要么同时存在于两台主机(常规的热备/温备做法),要么外部化到一个专门的密钥管理服务(HSM/KMS)按需签名而不落地私钥文件。两者都是这个项目今天完全没有的新组件或新运维动作,第五节展开。

本文档不代为做出这个选择——这是一条安全设计决策,理应由维护者在权衡"零停机的价值"与"私钥暴露面扩大"之后拍板,不应该被一份评估文档单方面定下来。第五节给出的候选方向都标注了各自在这条张力上站的是哪一边。

## 四、根据实际规模评估:与 Tunnel Gateway 评估同样的结论——没有证据支撑复杂方案

沿用[独立 Tunnel Gateway 评估](2026-09-18-p2-tunnel-gateway-event-infra-evaluation.md) §一 已经核实过的结论:[A01](2026-09-14-a01-scope-reliability-design.md) 明确记录项目至今没有跑过真实生产负载,没有节点数/吞吐量实测数据;[A02](2026-09-14-a02-disaster-recovery-key-rotation-design.md) 与 P07 均确认"当前无生产租户阶段"。这对 Registry HA 评估的直接影响:

- 没有真实数据回答"Registry 故障窗口期间,有多少次节点注册/续期/吊销尝试因此被阻塞、造成多大影响"——[A01](2026-09-14-a01-scope-reliability-design.md) §3.4 把整块 Registry 故障行为标注为"设计推断,没有故障注入测试"(A01:190)。
- 证书 30 天有效期本身就是一个"设计上刻意放宽的窗口"(README:26 的签发逻辑),没有生产数据能证明这个窗口对当前场景是否已经足够宽松到不需要多活。

**结论与 Tunnel Gateway 评估一致:不建议现在投入实现一套多活 Registry(方案 (b)/(c)/(d),见第五节)。** 理由同样不是"规模太小",而是没有证据支撑更复杂方案的收益超过它的成本(新的安全暴露面、新的一致性协调复杂度、可能违反 AGENTS.md 依赖红线)。第一节已经指出,现状的"重启 + 证书容忍窗口"组合本身有真实验证数据支撑,是比"没有数据支撑、但架构更复杂"的多活方案更站得住脚的现状。

## 五、候选方向评估(供未来触发时参考,不在本项范围内选定)

| 方向 | 私钥归属 | 一致性机制 | 依赖红线影响 | 何时值得考虑 |
| --- | --- | --- | --- | --- |
| (a) 维持单实例,只强化自愈(K8s/进程监视器 + 健康检查 + 更快重启) | 单进程,不变 | 不适用——任意时刻只有一个进程在跑 | 无新增依赖 | 默认推荐;详见第一节第 2 点,已有真实 RTO 数据支撑 |
| (b) 把 tokenstore/identitystore 的状态外部化到控制面已有数据库,Registry 变薄 | **仍只能单进程持有**——外部化状态解决不了私钥本身的复制问题 | 控制面的 gorm 事务/行锁(P07 已有的固定版本 SQL 迁移模式) | Registry 新增一次 HTTP 调用(可复用 Gateway `controlplaneclient` 已确立的"只用标准库 `net/http`"先例,不违反依赖红线),但**新增了 Registry 对控制面可用性的依赖**——今天两者是正交的故障域(架构图里 Registry 与控制面之间没有连线),这个方向会改变这一点,是一项需要单独评估的架构代价,不是免费的 |
| (c) 主备复制:standby 通过 gRPC 接收 primary 的状态变更流(类比 `GatewayRoster` 广播机制),故障时提升为 primary | 私钥要么在 standby 也常驻(违反第三节"单进程持有"的现状声明,需要显式改写这条安全设计),要么 standby 是"冷备"(不加载私钥,提升时靠运维手动介入完成密钥物料交接) | 自建的 leader 选举——没有外部协调服务(etcd/Consul 等)的话很难避免脑裂 | 不新增外部消息队列/DB 依赖,但"自建 leader 选举"本身是相当分量的新代码,且正确性难以在没有真实故障注入环境下验证 | 只有在方向 (a) 被证明不够、且团队愿意承担"单进程持有"这条安全声明被改写的代价时才考虑 |
| (d) 私钥外部化到 HSM/KMS,Registry 按需调用签名 API 而不落地私钥文件 | 私钥不再由任何 Registry 进程本地持有 | 依赖外部 KMS 自身的可用性 | 新增一个外部服务依赖,且很可能需要新的客户端库(视 KMS 选型而定,超出"gRPC/protobuf"这条线) | 长期方向,但引入全新的信任边界和运维复杂度,不是"高可用"这一个诉求单独能撑起的决定,更像是与密钥轮换([A02](2026-09-14-a02-disaster-recovery-key-rotation-design.md) 已核实"CA 轮换本身无代码路径")一起考虑的独立课题 |

**四个方向里,(b) 和 (c) 都无法回避第三节的核心张力——私钥依然只能有一个进程真正持有/使用它,"高可用"能做到的只是缩短从"检测到故障"到"另一个进程接管"之间的时间,不是真正的多活签发。** 这个上限是密码学私钥的本质决定的,不是工程实现能绕开的,任何后续方案的验收目标都不应该承诺"零停机签发",只能承诺"更短的故障切换时间"。

## 六、若未来推进,建议的任务拆分(不在本项范围内交付)

1. **先把方向 (a) 的验收做实**:给 A01 §3.4 标注的"设计推断"补上真实故障注入测试(关掉 Registry 进程,验证已建立隧道确实不受影响、新注册确实阻塞、Registry 恢复后名册确实重新同步),这是与"是否需要更复杂的多活方案"直接相关的证据,应该先做,不依赖后续方向如何选。
2. **由维护者裁决第三节的安全设计取舍**:私钥"单进程持有"是否可以放宽、放宽到什么程度(温备常驻 vs 仅故障时物料交接 vs 外部化到 KMS),这条决策的影响面覆盖整个 Registry 的信任模型,不应该由后续实现任务顺带做出。
3. **若选定方向 (b)**:设计 Registry→控制面的内部 API(鉴权、幂等写入模式,类比 Job/UsageRecord 已有的 `InternalToken` 守卫先例),并评估 bootstrap token 明文进入控制面数据库的脱敏/保留期要求(不能直接照搬 `apikey` 包的哈希模式,因为 tokenstore 需要在 `Consume` 时比较原文,除非改成"哈希存储 + 提交时重新哈希比对"的模式,这本身是一项子设计)。
4. **若选定方向 (c)**:设计状态变更的 gRPC 广播协议(复用 `GatewayRoster` 广播已验证的单调版本号模式)与 standby 侧的 leader 选举/提升机制,并给出脑裂场景下的行为定义(例如短暂网络分区时两个进程都自认为 primary,如何保证不会有两份冲突的 `node_id` 绑定被同时接受)。
5. **补齐 [A02](2026-09-14-a02-disaster-recovery-key-rotation-design.md) 已记录的相邻缺口**:CA 轮换本身无代码路径、密钥轮换无过渡期——这两项与 Registry HA 有交叉(轮换期间如何保证在途签发不受影响,在多活场景下更复杂),值得放在同一批评估。

以上五项彼此有依赖顺序:1 独立可先做;2 是 3/4 的前置门槛;5 可与 1 并行。不建议在没有第 1、2 两项的结果之前直接开始实现 3 或 4。

## 七、已知缺口清单

1. **第一节"重启 RTO 是否已经足够"没有量化验收标准**——A01/A02 给出的是观测数据(约 3 秒),不是一个经过运维/业务方确认的目标值;"这个窗口是否可接受"本身依赖尚不存在的生产 SLA,与第四节"无真实规模数据"是同一处境的两种表现。
2. **第三节的安全设计取舍没有默认答案**——本文档刻意不替维护者做这个决定,这是本项唯一"评估未能给出唯一结论"的地方,如实记录而非强行给出一个看似完整但缺乏授权的选择。
3. **方向 (b) 的 bootstrap token 脱敏方案未设计**——第六节第 3 条只指出了问题(需要在 `Consume` 时比较原文,与哈希存储天然冲突),没有给出具体方案。
4. **方向 (c) 的脑裂场景行为未定义**——第六节第 4 条同样只列出了需要回答的问题。
5. **没有真实故障注入测试**——与 A01 §3.4 的既有缺口相同,本文档没有新增任何测试来填补它,留给第六节第 1 条。
6. **未评估 Console/控制面侧 P01(节点审批)、S02(令牌绑定)等已有功能在方向 (b)/(c) 下如何变化**——这些功能今天都假设"一个 Registry 进程"是权威来源;方向 (b)/(c) 一旦落地,需要重新核对每一处调用 `TokenAdmin`/`NodeIdentity` 的既有代码在多进程场景下的行为,本文档未逐一核对,留给具体实现任务。
