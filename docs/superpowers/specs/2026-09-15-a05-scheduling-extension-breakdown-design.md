# A05 调度扩展拆分

本文档交付根 STATUS.md「规划补充」A05：按实际负载评估最少在途请求、延迟/成本评分、租户节点池和会话亲和；受信任授权与 Agent 自报标签分开，依赖 P01/P02 及资源采集，不能把现有加权路由视为全部完成。

范围边界：**本项以设计文档为主，不含新代码或新测试**，与 [A01](2026-09-14-a01-scope-reliability-design.md)、[A04](2026-09-15-a04-direct-mode-boundary-design.md) 同一先例。理由同样是 STATUS.md 用词本身——"评估""拆分""分开"是核实现状并划边界，不是"实现"；而第一节的盘点结果是：调度器今天完全不接收租户身份（`Scheduler.Chat` 等方法签名里没有 tenant 参数），会话亲和所需的会话概念在 Chat/Embed 路径上不存在，延迟评分唯一可用的信号（`runtime.HealthReport.Latency`）已经存在但从未接入排序，租户节点池所需的"受信任授权"与"Agent 自报标签"在代码里已经是两个刻意分离的概念、只是后者尚无消费者。要把这四项做成能跑的功能，分别需要改 `Scheduler` 的方法签名、`httpapi` 到 `scheduler` 的调用链、控制面新增的租户节点池数据模型，以及一套会话亲和失效策略——每一项工作量都独立成立，不是可以在核实过程中顺手写完的补丁。凡属阅读代码得出的结论标注文件:行号；仅在 README/STATUS 散文中出现、找不到代码依据的一律计入第八节缺口清单，不采信为现状。

## 一、现状盘点

### 1.1 README「调度策略的规划范围」七项逐一核对

README.md:460-468 列出七项调度策略规划：

| 策略 | 状态 | 代码依据 |
| --- | --- | --- |
| 加权轮询 | 已实现 | `weightedCandidates`（`scheduler.go`），按 `target.Weight` 在同优先级候选间随机加权选择 |
| 最少正在执行请求 | 已实现 | `pickBy`（`scheduler.go:397-454`）排序键：`idle` 降序、`inflight` 升序 |
| 节点优先级 | 已实现 | `routing.Target.Priority`，外层优先级分组、内层才做权重/负载启发（`scheduler.go:331-334` 注释已说明该分层设计） |
| 节点标签路由 | 已实现 | `Target.MatchesNode`（`common/modelroute/modelroute.go:39-47`），`pickBy` 在遍历节点的第一步调用（`scheduler.go:419`） |
| 租户绑定节点或节点池 | **未实现** | 见 1.3 节 |
| 会话亲和 | **未实现** | 见 1.4 节 |
| 连续失败熔断和自动恢复 | 已实现 | `s.breakers`（`scheduler.go` 引用 `breakerRegistry`），`pickBy` 在候选进入排序前调用 `s.breakers.eligible` |

STATUS.md 对 A05 的措辞——"不能把现有加权路由视为全部完成"——在这张表里得到坐实：七项里五项已经做完，但"租户节点池"与"会话亲和"两项是结构性缺失，不是可以靠调参数补齐的细节。

### 1.2 受信任授权与 Agent 自报标签：代码里已经是两个概念，只是后者无消费者

`tunnelserver.NodeInfo.Labels` 的 doc comment（`node.go:158-164`）逐字写着：

> Labels are the operator-assigned facts the Agent declared, which routing rules select on. They are a preference about where work should go, never permission to receive it: a compromised Agent could claim any label.

`node` 结构体内部字段 `labels`（`node.go:44-50`）的注释更直接："labels 是 Agent 在 Hello 中声明的内容。它们被原样采信，且绝不能参与授权判断"。`common/nodeview.Node.Labels`（`nodeview.go:95-101`）对外暴露给 Console 时重复了同一句警告。README.md:442 把这句话提炼成一句架构原则："节点标签是偏好，不是权限。Agent 自报标签只用于调度筛选。租户是否可以访问某模型、模板或节点池，必须由受信任的授权配置决定。"

也就是说，"标签是偏好、不是权限"这条边界在代码注释和 README 里已经被反复声明、并且被 `MatchesNode`（`common/modelroute/modelroute.go:39-47`）的实现严格遵守——它只做字符串匹配，从不隐含授权语义。**缺失的不是这条边界本身，而是边界另一侧："受信任的授权配置"在哪里、长什么样**。今天全仓库没有任何结构把"某租户只能用某些节点"表达成一份配置：`modelroute.Route`/`Target` 没有 tenant 字段；`common/quota.Limits`（P05/P06 已实现的租户配额）只管请求数/token 数/并发，不涉及节点范围；P01 的节点审批/禁用/维护（`identitystore`）是全局状态，不分租户。

### 1.3 租户节点池：调度器今天完全不知道请求属于哪个租户

`Scheduler.Chat`（`scheduler.go:151`）、`Embed`（`scheduler.go:176`）、`ChatStream`（`scheduler.go:207`）三个方法的签名都是 `(ctx context.Context, req runtime.ChatRequest/...)`，没有 tenant 参数；内部调用链 `candidates` → `candidatesWith` → `candidatesWithRandom` → `pick` → `pickBy` 同样全程不携带租户身份。

租户身份在 Gateway 里确实存在，但只活在 httpapi 层：`IdentityFrom(ctx)`（`ratelimit.go:72`）从请求上下文取出 `identity.TenantID`，用于 `rateLimit` 中间件按租户执行配额（`ratelimit.go:67-100`）。这个中间件包在 `handlers` 上，处于 HTTP handler 链路里，但它把请求交给 `next.ServeHTTP` 之后，租户身份就不再往下传——具体的 chat/embed handler 调 `Scheduler.Chat` 时，传的只是 `runtime.ChatRequest`，租户信息在这一跳被丢弃。

这意味着 README 调度流程图（README.md:446-458）里"检查租户和节点访问权限"这一步，在今天的调用链上**没有对应的代码位置**：它画在"过滤能力不匹配节点"和"按优先级、负载、延迟和成本评分"之间，但 `pickBy` 循环遍历节点时（`scheduler.go:409-440`）没有任何入参能回答"这个节点对当前租户是否可见"。要让这一步存在，必须先把租户身份一路带到 `pickBy`，这本身就是一处方法签名改动，牵动 `Scheduler` 的公开 API 和 `httpapi` 的每个调用点。

### 1.4 会话亲和：Chat/Embed 路径没有会话概念，`SessionID` 是另一个不相关的既有名字

全仓库唯一的 `SessionID` 是控制面登录会话（`token.Claims.SessionID`，`token.go:45`），服务于 Console 用户/运维登录态的吊销（P05），与推理请求毫无关系。OpenAI 前门的 Chat/Responses/Embeddings 三个端点里，Responses 本应是最适合承载会话概念的入口，但 README/STATUS 已经反复确认"Responses 不支持持久会话续接"（AGENTS.md 代码地图行、STATUS.md:27），`store`/`previous_response_id` 被前门显式拒绝——即便客户端传了这两个字段，请求也不会被当成同一会话的延续。工作流 Job 有"稳定路由绑定"（J06 的 `observed_seq`/路由持久化），但那是"同一个 Job 的多次状态轮询要打到同一个执行位置"，不是"同一个最终用户的多轮对话要打到同一个节点"，两者语义不同、代码路径也完全不同（Job 走 `scheduler/workflow.go`，Chat 走 `scheduler.go` 的 `Chat`/`ChatStream`）。

因此会话亲和不是"已有半成品、需要补全"，而是要从零定义：以什么为会话标识（客户端自带的会话 ID？API Key 维度的粘性？）、亲和失效策略（节点下线/熔断后退回普通调度）、以及与现有"流式响应首 token 前才可重试"规则（README.md:470）的交互——这条规则已经隐含了一种弱亲和（同一次请求的重试尽量不切节点），但和"同一用户多轮对话尽量打到同一节点以复用 KV Cache"是两个不同粒度的问题。

### 1.5 延迟/成本评分：延迟已有一个现成但未使用的信号，成本完全不存在

`runtime.HealthReport.Latency`（`common/runtime/types.go:74-82`）是健康探测的往返延迟，`nodeview.FromSnapshot`（`nodeview.go:224-228`）已经把它渲染给 Console 展示（`view.LatencyMillis`）。但 `pickBy` 循环里能拿到的 `snap runtime.Snapshot`（`scheduler.go:423`）虽然携带 `snap.Health`，排序逻辑（`scheduler.go:442-447`）只用了 `idle` 和 `inflight` 两个字段，从未读取 `snap.Health.Latency`。这是一个**已经存在、只是没有被接进排序**的信号，但它的语义是"周期性健康探测的往返时间"，不是"实际推理请求的服务时延"——两者会在负载升高时明显背离（探测请求通常走轻量端点，不排队；推理请求会排队等空闲槽）。`scheduler/metrics.go` 的 `Dispatch` 方法（`metrics.go:155-160`）只记录成功/失败计数，没有按候选记录请求耗时直方图，所以"真实服务时延"这个更准确的信号，今天在调度器里完全不存在，需要新增记录点才能获得。

成本评分则没有任何现成信号：全仓库没有 `Cost`/`Price` 相关字段，`routing.Target`/`modelroute.Target` 也没有成本维度。README.md:454 把"成本"和"延迟"并列写进调度流程图，但这是规划意图，不是已有的部分实现。

### 1.6 资源采集：已采集的是静态硬件清单，不是实时利用率

`tunnelv1.NodeResources`（`api/proto/tunnel/v1/tunnel.pb.go:2507`）携带 `CpuCores`/`MemoryBytes`/`GpuCount`/`GpuMemoryBytes`/`Os`/`Arch`，在 Hello 握手时上报一次（`node.go:38` 的 `resources *tunnelv1.NodeResources` 字段，未见在 `Heartbeat`/`applyStatus` 路径中被更新——`Heartbeat` 消息本身只有 `SentUnixMs`/`InflightRequests`/`IdleSlots` 三个字段，`tunnel.pb.go:2643-2650`，不携带资源数据）。这是一份**静态硬件容量声明**，回答"这台节点理论上有多少资源"，不回答"此刻还剩多少可用显存/内存"。STATUS.md P2 待办第五条——"GPU/显存和系统资源采集、资源感知调度，以及有界任务排队"——描述的正是后者，尚未开发。A05 依赖它，是因为"按实际负载评估"如果要超越"idle slots/inflight 请求数"这两个粗粒度信号，理应用上真实的显存/内存占用，而这份数据目前不存在于心跳协议里。

## 二、受信任授权与 Agent 自报标签分开：设计原则

沿用第 1.2 节已经确认、并被代码严格遵守的边界，本节把"受信任的授权配置"补上一个具体形状，供未来实现租户节点池时使用。

1. **两份配置永远是两个数据源，不允许合流。** `NodeSelector`（标签匹配）继续只读 Agent 自报的 `node.labels`，用于运维"这个模型倾向于用这类机器"的偏好表达；租户可见节点集合读一份新的、只能由受信任方写入的配置（下称"租户节点池"），两者在 `pickBy` 里是两次独立的过滤，不能把标签匹配的结果直接当成授权结果，也不能让标签值决定某个租户是否可见某节点。
2. **写入路径必须落在 P01/P02 已有的"受信任写入"同一等级。** P02 的路由发布已经建立了一套模式：控制面 CAS 发布 + 原子审计 + Gateway 有界拉取/持久缓存/热切换（STATUS.md P02 行）。租户节点池的写入应复用同一模式，而不是走 Agent 心跳或任何 Agent 可影响的路径——这与第三节地址允许列表在 A04 文档里的"所有权原则"是同一类判断：凡是决定"谁能访问什么"的配置，写入方必须是运维/控制面，绝不能是被调度的对象自己。
3. **默认值应是"未配置 = 不限制"而非"未配置 = 拒绝全部"。** 这与 A04 文档第三节地址允许列表"默认拒绝"的结论**相反**，原因是威胁模型不同：A04 的地址允许列表防的是"网络可达但未经批准的后端"，默认拒绝是因为可达不等于批准；租户节点池要表达的是现有部署的多数场景——租户与节点池是可选的细分能力，不配置时应退回现有的"全体在线节点参与调度"行为，否则任何尚未升级配置的现网部署都会在功能上线当天变成"所有请求无候选"。这一条差异需要在实现时显式测试覆盖，避免直接照搬 A04 的默认拒绝结论。
4. **标签仍然可以作为节点池*内部*的筛选维度。** 一个节点池圈定"哪些节点对某租户可见"之后，`NodeSelector` 继续在池内部按标签做进一步收窄（例如"这个租户的池子里，优先用 `region=local` 的机器"）。这保持了第 1.2 节强调的分层：标签管偏好，池子管权限，两层职责不重叠。

## 三、租户节点池：设计草案

1. **数据形状建议对齐 `modelroute.Target` 已有的量纲控制**，而不是发明新的容量模型：`common/modelroute` 已有 `MaxRoutes`=1000、`MaxTargets`=100、`MaxRoutesBytes`=1MiB 等边界（`modelroute.go:16-28`），租户节点池若新增独立配置对象，应给出同等量级的显式上限，不能是无界列表。
2. **归属哪个服务，需要在实现前明确**：候选是（a）挂在 `common/modelroute.Target` 上新增一个 `TenantSelector`/`AllowedTenants` 字段，随路由发布一起走 P02 已有的 CAS 流程；或（b）独立于路由表的一份"租户 → 节点池"映射，类比 P01 节点状态但按租户分维度。两种设计对现有 `routing.Table.Resolve`（`routing.go`）的改动幅度不同：方案（a）复用现有结构，改动小；方案（b）需要 `pickBy` 额外接一次查询。本文档不替未来实现选定，但指出方案（a）与"标签管偏好、池子管权限"的分层原则（第二节第 4 条）更契合，因为它让租户维度和节点选择器维度在同一个 `Target` 里并列存在，而不是让调度器在两套独立配置间做交叉查询。
3. **鉴权信息必须先到达 `pickBy`。** 无论选哪种数据形状，`Scheduler.Chat`/`Embed`/`ChatStream`/`pick`/`pickBy` 的方法签名都需要新增一个租户参数（或者把 `runtime.ChatRequest` 一类请求结构体扩展出租户字段——但这类结构体目前是协议无关的运行时请求，混入租户身份会打破它现有的"协议层不感知租户"边界，更合理的做法是作为独立参数传递，与 `ctx` 分开而不是塞进 `ctx.Value`，保持依赖显式可见）,`httpapi` 的 chat/embed handler 需要把 `IdentityFrom(ctx)` 取到的租户身份显式传下去，而不是像今天这样止步于 `rateLimit` 中间件。这是一处跨越 `httpapi` 与 `scheduler` 两个包的接口变更，必须整体设计签名后一次性改完，不能先改一半。

## 四、延迟/成本评分：设计草案

1. **延迟评分应先用已有信号做一版低成本实现，再评估是否需要新增服务时延埋点。** 第 1.5 节指出 `snap.Health.Latency` 已经存在但未接入排序；一个渐进式设计是在 `pickBy` 现有的两级排序键（`idle` 降序、`inflight` 升序）之后追加第三级键（`Health.Latency` 升序），作为前两级打平时的 tie-breaker，而不是替换现有排序——这样能以最小改动验证"探测延迟能否近似反映真实服务质量"，同时保留 README.md:463 已承诺的"最少正在执行请求"策略不被打乱。若验证后发现探测延迟与真实服务时延偏差过大（第 1.5 节已指出两者在高负载下会背离），再评估是否需要在 `recorder.Dispatch` 旁新增一个按候选记录的时延直方图（类似 `scheduler/metrics.go` 现有 `MetricCandidates` 直方图的模式），并用它反哺调度决策——但这属于"先有数据、再决定怎么用"的迭代，不应在数据不存在时就设计消费逻辑。
2. **成本评分需要先有成本模型，这不是调度器能独立解决的。** 成本通常取决于节点的部署形态（自有硬件 vs 按量计费的云 GPU）、计费周期与租用协议，这些信息今天不存在于 `NodeInfo`/`routing.Target` 的任何字段。在有一个明确的"每节点/每 target 成本值从哪来、谁维护"的答案之前，调度器不应该发明一个占位分数——一个凭空定义的成本模型比完全不做成本评分更危险，因为它会让调度决策看起来有依据、实际却是噪声。本文档因此把成本评分列为**需要先由运维/产品侧定义成本来源**的前置问题，而不是一处可以直接给出排序公式的设计点。

## 五、会话亲和：设计草案

1. **会话标识需要先由 API 层定义，调度器不能替客户端发明一个。** 结合第 1.4 节的核实结果，最贴近现状的落点是：如果未来 OpenAI 前门要支持会话亲和，应该复用或参照 Responses 已经预留但当前拒绝的 `previous_response_id` 语义，把它从"拒绝"改造成"提示调度器优先复用上次的候选"，而不是新发明一个亲和专用字段——这样能同时解决"会话怎么标识"和"会话亲和只对支持会话的端点生效"两个问题。Chat Completions 端点在 OpenAI 协议里本身无状态，若要支持亲和，需要客户端自带一个稳定标识（例如请求头），这已经超出 OpenAI 协议兼容的范围，需要额外评估是否值得做成非标准扩展。
2. **亲和是尽力而为的提示，不是强约束——这条设计原则可以直接对齐现有熔断/重试的既有语义。** `pickBy` 的候选列表已经是"尽力排出最优序"而非"唯一解"：熔断会跳过候选（`s.breakers.eligible`），重试会切换候选（`retryable(err)`）。会话亲和应该表现为"把上次的候选提到候选列表最前面，而不是过滤掉其他候选"——这样在亲和目标不可用时（节点下线、熔断跳闸、维护），现有的重试与候选遍历逻辑不需要任何改动就能自然退回到普通调度，不需要为亲和失效单独设计一套降级路径。
3. **流式请求的"首 token 前才可重试"规则（README.md:470）与会话亲和需要合并成一套一致的语义**，避免调用方在两条规则间猜测行为：同一次请求内的重试是"这次调用还没产生输出，换一个节点重试"；跨请求的会话亲和是"上一次调用产生过输出，这一次调用应该优先回到同一个节点，但如果那个节点不可用就正常走候选遍历"。两者的共同点是都不承诺切换后输出连续，只是尽力减少不必要的节点切换。

## 六、验收目标（供未来实现该功能时使用；本项不实现）

A05 若要在未来分拆出的实现任务中交付，至少需要满足：

1. `Scheduler` 的 `Chat`/`Embed`/`ChatStream` 方法签名（或其调用约定）携带租户身份，`httpapi` 到 `scheduler` 的调用链有测试覆盖"同一模型对不同租户返回不同候选集"。
2. 租户节点池的写入路径复用 P02 同等强度的 CAS 发布 + 审计，且有测试覆盖"平台运维发布节点池 → Gateway 拉取生效 → 调度器按池子过滤候选"的端到端链路；未配置节点池的现有部署行为不变（对齐第二节第 3 条）。
3. `pickBy` 排序追加延迟维度后，有测试覆盖"两个候选 idle/inflight 相同、探测延迟不同时，延迟更低者优先"，且不改变现有 `idle`/`inflight` 两级排序的既有测试预期。
4. 会话亲和的候选重排有测试覆盖"亲和目标不可用时自动退回普通候选顺序"，以及"亲和信息不影响熔断/重试的既有判定"。
5. 成本评分在有明确成本来源定义之前不实现占位公式；若后续任务引入成本来源，需先补一份独立设计说明其数据来源与更新频率，再接入排序。
6. README.md:444-468 的调度流程图与"规划范围"列表，随每一项实际交付更新状态标注，不在功能完成前提前标注为已实现。
