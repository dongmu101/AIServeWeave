## 一、Registry CA/注册状态：备份恢复演练（已实测）

### 1.1 持久状态的真实位置

Registry 的全部持久状态收在一个 `-data-dir` 之下（默认 `./data/registry`，`service/aiServeWeaveRegistry/main.go:71`），三个子存储各自独立打开，没有共享的"存储抽象层"：

| 内容 | 路径 | 格式 |
| --- | --- | --- |
| CA 根私钥 | `<data-dir>/ca/ca-key.pem` | PKCS8 PEM，权限 `0o600` |
| CA 根证书 | `<data-dir>/ca/ca-cert.pem` | PEM，权限 `0o644` |
| 注册令牌账本 | `<data-dir>/tokens.json` | 纯 JSON 数组，原子写（临时文件+`Sync`+`rename`），权限 `0o600` |
| 节点身份账本 | `<data-dir>/identities.json` | 同上 |

`identitystore`/`tokenstore` 包文档明确写着"假设只有一个 Registry 进程"、"一致性来自一把内存互斥锁加一个原子写文件，不是分布式存储"（`internal/identitystore/identitystore.go:23-27,45-47`）。CA 没有序列号台账：`randomSerial()`（`internal/ca/ca.go:252-261`）每次签发只是抽一个随机 128 位数，不落盘、不去重记录。

### 1.2 演练：对正在运行的参考部署（`deploy/docker-compose.yaml` 的 `registry` 服务）做一次真实的丢失+恢复

没有用合成测试，而是对着本机已经在跑的 `deploy-registry-1` 容器（挂载真实的 `deploy_registry-data` 卷）动手：

1. 用 `-mint-token` 客户端模式（`service/aiServeWeaveRegistry` 的 CLI，指向 `127.0.0.1:9443`，用容器里现成的 `admin-token`）对运行中的 Registry 铸造一枚真实的 bootstrap 令牌，产生真实的 `tokens.json` 状态。
2. `docker exec ... tar -czf ... /data` 打一份完整备份，作为恢复点。
3. **第一次尝试**：直接删掉容器内的 `tokens.json`，不重启进程，立刻用 `-revoke-token` 去撤销刚才那枚令牌——**撤销成功**，且撤销之后 `tokens.json` 被重新写回磁盘。
4. **这是一个值得记录的真实发现，不是预期外的失败**：Registry 进程把整个令牌账本读进内存后就不再依赖磁盘文件本身，磁盘文件只在下一次变更（Mint/Consume/Revoke）时被原子重写。因此"文件在磁盘上被删除/损坏"这件事本身**不构成数据丢失**，只要进程不重启，内存态还在，下一次任何写操作都会把文件重新种回去。真正的丢失窗口是"文件已经不完整、且进程重启/崩溃后重新从磁盘加载"这一刻，不是文件损坏发生的那一刻——这个区分此前没有在任何 README 或 STATUS 条目里写过，直接影响下面的 RPO 定义。
5. 重新铸造一枚新令牌（`c3PE_...`）作为第二次演练的恢复点基线，再打一份备份。
6. 这次**真正**制造丢失：删除 `tokens.json` 后用 `docker restart` 重启容器进程（而不是仅仅删文件）。重启日志显示进程在约 3 秒内完成关闭与重新起来（`shutdown signal received` 到 `registry started` 相隔 3 秒，两次独立观测到同样约 3 秒的量级）。
7. 重启后确认令牌确实丢了：用 `-revoke-token` 撤销该令牌，返回 `rpc error: code = NotFound desc = token is unknown`——证实第 6 步真的造成了数据丢失，不是自愈。
8. 恢复：`docker stop` → 把第 5 步的备份 tar 解压回容器的 `/data` → `docker restart`（确保进程重新从磁盘加载，而不是靠内存里还留着旧状态侥幸通过）。
9. 恢复后重新撤销同一枚令牌——**成功**，证明备份/恢复的往返是有效的。
10. 全程用 `sha256sum` 核对 `ca-cert.pem`/`ca-key.pem` 在演练前后字节级一致——CA 材料从未被这次演练触碰或损坏，本身也证明了"备份/恢复 CA 目录"这个最关键的资产是可行的。

**结论（已验证，非设计意图）**：

- Registry 的三块持久状态（CA、令牌账本、身份账本）都是纯文件、原子写，`tar` 打包整个 `-data-dir` 就是一份完整、可用的备份；恢复只需要把 tar 解压回同一路径再重启进程。
- **RPO 的真实边界是"进程重启"，不是"文件损坏"**：只要 Registry 进程本身没有重启，一次外部对数据文件的破坏是可以被下一次正常的写操作自愈的；只有在文件已经丢失/损坏**且**进程随后重启（崩溃、升级、迁移）的组合下，数据才真正丢失，丢失范围等于"最后一次成功持久化写入"到"进程重启那一刻"之间的全部变更——考虑到每次 Mint/Consume/Revoke/Approve/Disable/Enable 都同步落盘（不是定时批量刷盘），这个窗口在正常运行时几乎为零，真正有意义的场景是"备份本身就是从一个已经部分损坏的卷做的"，而不是"两次写操作之间发生了什么"。
- 观测到的 RTO（单容器重启，不含备份提取时间）约 3 秒；这是本机单机场景下的观测值，不是多副本/编排环境下的生产 RTO 承诺，仓库里也没有更大规模的验证证据。

### 1.3 已知未覆盖的部分（沿用已确认的代码事实，未新增验证）

- **没有 CA 轮换代码路径**：`ca.go:34-37` 的注释原文承认"轮换根证书意味着给每个节点重签证书，Registry 目前没有为此准备任何工具"。本次演练只验证了"备份并原样恢复同一份 CA"，不涉及、也无法涉及轮换根 CA 本身——那是一个不存在的功能，不是一个可以演练出结果的操作。
- **没有 CRL/OCSP**：Registry README 已经写明"证书在到期前始终密码学有效"，禁用只靠名册广播。备份恢复这条链路不会改变这一点：从旧备份恢复出来的 Registry，其身份账本里"已禁用"的节点会正确恢复为禁用状态（因为这是 `identities.json` 里的字段，随文件一起备份），但如果备份点早于某次禁用操作，恢复后的 Registry 会把一个本该禁用的节点当作仍然合法——这与数据库回退后"必须依据独立保留的安全记录重放吊销"（`database-recovery.md:70`）是同一类问题，Registry 侧目前没有对应的运维手册段落，本文档在下面「运维手册」一节补上。

## 二、对象存储：备份恢复与账物一致性演练（已实测，脱离参考部署单独验证）

### 2.1 为什么没有用参考部署做这部分演练

调查确认 `deploy/docker-compose.yaml` 和 `deploy/.env.example` 都没有配置任何对象存储后端（`AllowedUploadExtensions` 之外，压根没有 S3/WebDAV/本地目录相关的环境变量或卷挂载）——P04 的持久化产物存储在当前参考部署里实际上**没有被启用**。这本身是一处值得记录的部署缺口（见第四节）。因此这部分演练改用 `service/aiServeWeaveGateway/objectstore` 包本身，在独立的临时目录里直接调用真实的 `Local` 后端实现（不是 mock），贴着 P04 的真实 key 构造方式（`{tenant_id}/{job_id}/{artifact_id}`，见 `httpapi/jobpersist.go:508`）搭一个最小可复现场景。

### 2.2 演练设计与结果

用真实的 `objectstore.NewLocal`/`Put`/`Open` 跑了一段脚本（未合入仓库，跑完即删除），模拟两个真实运维场景：

**场景一：对象存储的备份点早于数据库**（数据库和对象存储各自独立备份周期，这正是仓库目前的实际情况——P07 只管数据库，对象存储没有任何备份编排）

1. T1：job_a 提交，写入 `art_1`、`art_2` 两个对象，同时"数据库"（此处用一份 JSON 清单模拟 `job_artifacts` 表）记录两行。
2. 对存储目录打 tar 备份（T1 备份点）。
3. T2：job_b 提交，写入 `art_3`，数据库清单增至三行。
4. 灾难发生，数据库本身在 T2 之后完好恢复（走 P07 流程），但对象存储只能从 T1 备份恢复（比如对象存储的备份编排比数据库更旧，或者两者用不同的备份保留策略）。
5. 恢复后逐行核对：`art_1`、`art_2` 用 `sha256sum` 独立验证与原始内容**字节级一致**；`art_3` 打不开，返回 `objectstore: object not found`。

这正是 `deploy/database-recovery.md:68` 早就提醒过的方向（"产物元数据还需对照对象存储字节，P07 演练不保证文件存在"），本次演练把它从一句提醒变成了一个可复现的具体结果：**恢复后必须用 `job_artifacts.storage_key` 逐行探测对象是否存在，不能假设数据库恢复成功就意味着产物都在**。

**场景二：反方向——数据库恢复到较早的备份点，但对象存储没有丢失，停留在较新状态**

6. 把数据库清单"回退"到 T1（模拟一次数据库层面的灾难恢复，把 job_b 那一行连同它之前更早的误操作一起回退掉了），对象存储保持在 T2（存储本身没有出故障，不需要恢复）。
7. 核对：`art_3` 这个对象在存储里依然存在且可读，但回退后的数据库清单里已经没有对应的行。

这个方向此前**没有在仓库任何地方讨论过**——之前只谈到"数据库恢复后产物可能缺失"，从没谈过"数据库恢复后可能多出没人认领的对象"。这类悬空对象不会主动造成错误（不会有人尝试去读一个不存在的行所指向的 key），但会静默占用存储空间，且没有任何回收机制能发现它们：`artifactcleanup.go` 的保留期清理是按数据库里的行去删对应字节（`reap` 逻辑，`artifactcleanup.go:225-240`），从数据库出发单向清理，从来不会反过来扫描"存储里有、数据库没有"的对象。

### 2.3 结论

- **备份恢复本身是可靠的**：`Local` 后端只是文件系统上的文件，`tar` 打包整个存储根目录、原样解压回去，内容字节级一致，本次演练用独立 `sha256sum` 核对过，不依赖程序自己的"看起来打开成功了"这种弱验证。
- **账物一致性没有任何自动化保障，两个方向都会真实发生**：
  1. 对象存储恢复点早于数据库 → 数据库有行，对象缺失（已被 `database-recovery.md` 提醒，本次给出可复现验证）。
  2. 数据库恢复点早于对象存储 → 对象存在，数据库无行（此前未被讨论，本次首次记录）。
- 两个方向都没有对账工具。运维手册（第五节）给出恢复后必须执行的人工核对步骤；是否要做一个自动对账脚本，留给后续任务按需评估，不在本次范围内动代码。

## 三、密钥/令牌轮换：现状确认与硬切换手册（不新增代码）

调查确认仓库里六个长期密钥（`AISW_ACCESS_SECRET`、`AISW_INTERNAL_TOKEN`、`AISW_BOOTSTRAP_TOKEN`、`AISW_CONSOLE_SESSION_SECRET`、`AISW_REGISTRY_ADMIN_TOKEN`、`AISW_GATEWAY_ADMIN_TOKEN`）以及 ControlPlane 的 JWT 签名密钥，全部是启动时加载一次的单一标量值，没有任何地方支持"新旧密钥并存"——用代码结构本身确认（`Config`、`AuthConf`、`Issuer` 等类型里都只有一个密钥字段，不是列表），也用全仓库范围搜索"接受多个有效密钥/过渡期"相关模式确认过没有命中。这意味着**轮换任何一个密钥，此刻都必须是全员同时切换的硬截止**，不存在灰度过渡：

| 密钥 | 影响范围 | 硬切换代价 |
| --- | --- | --- |
| `AISW_ACCESS_SECRET`（JWT 签名） | 所有租户/平台会话 | 旧密钥签发的 JWT 立即全部 `Parse` 失败；配合 Redis 会话表已有的"每账户最多 20 会话"设计，用户表现为需要重新登录 |
| `AISW_INTERNAL_TOKEN` | Gateway↔ControlPlane 全部内部调用（Key 校验、Job 读写、请求日志推送、吊销长轮询） | 必须 ControlPlane 与全部 Gateway 副本同时切换，否则旧副本的内部调用会被拒绝 |
| `AISW_CONSOLE_SESSION_SECRET` | Console 的租户与平台运维两种会话 Cookie（共用同一把密钥派生） | 所有已登录 Console 会话立即失效，需要重新登录 |
| `AISW_REGISTRY_ADMIN_TOKEN` | `TokenAdmin`（铸造/撤销/禁用/启用节点） | 与 ControlPlane 配置的 `Registry.AdminToken` 必须同时改，否则控制面对 Registry 的节点管理调用全部失败 |
| `AISW_GATEWAY_ADMIN_TOKEN` | `GatewayDirectory.Join` | 与 Gateway 侧配置必须同时改，否则新 Gateway 副本无法加入名册 |
| `AISW_BOOTSTRAP_TOKEN` | 控制面首次自举建号 | 只在全新部署时使用一次，正常运行期间的"轮换"没有意义 |

### 运维手册：硬切换步骤（每个密钥都遵循同一模式）

1. 生成新密钥值（`openssl rand -base64 32`），确认长度满足对应服务的最小长度校验（本文列出的几个共享密钥均要求 ≥32 字节）。
2. 选择一个可以接受短暂中断的维护窗口——硬切换意味着旧值失效到新值全员生效之间，依赖该密钥的调用会失败，不是可用性问题的边缘情况，是必然发生的短暂中断。
3. 按"先改被调用方、再改调用方"的顺序更新配置并重启：例如 `AISW_INTERNAL_TOKEN` 先重启 ControlPlane 再重启全部 Gateway 副本；`AISW_REGISTRY_ADMIN_TOKEN` 先重启 Registry 再重启 ControlPlane；顺序反过来会导致"调用方已经在用新值敲一个还在认旧值的服务"，中断时间只会更长。
4. 会话/JWT/Cookie 类密钥切换后，明确告知用户需要重新登录，而不是让他们自己发现 401/403 后去猜。
5. 切换完成后，检查各服务日志确认没有持续的鉴权失败（一次性中断是预期的，持续失败说明某个副本没有切换到位）。

**这份手册是当前唯一可行的方案，不是理想方案**——真正消除中断需要给这几个密钥引入版本化/多值校验支持，是一次会动到 ControlPlane、Gateway、Registry、Console 四个服务鉴权代码的改动，范围和风险都明显超出本次 A02 的既定边界（已与用户确认过，本次只交付设计与手册）。留给后续任务：如果要做，思路应该是「校验时接受一个新旧值的短列表，签发/铸造时只用最新值」，与仓库里 P06 吊销 generation、S02 令牌 TTL 等既有"新旧状态共存过渡"设计同一思路，不是本文档需要重新发明的东西。

## 四、服务端证书到期：一个演练中发现的真实运维隐患

调查确认一个此前没有被记录过的问题：参考部署 `deploy/docker-compose.yaml` 里，`registry-init` 一次性容器调用 Registry 的 `-issue-server-cert` 给 Gateway 的隧道监听端口签发服务端证书，而 `IssueServerCert` 复用的是 `NodeCertLifetime`（30 天），**不是** CA 自身的 10 年有效期。`registry-init` 的 `restart: "no"` 意味着它只在整个 compose 工程被重建时才会重跑一次，没有任何定时任务或到期前重签机制。也就是说，**任何照着这份参考部署原样起服务、超过一个月不重建工程的人，Gateway 的隧道监听证书会在 30 天后静默过期**，届时所有节点的新连接尝试会因服务端证书失效而失败——不是逐渐降级，是隧道监听整体不可用。

本次范围（设计+演练）不包含修代码。这里如实记录发现，并在运维手册里补一条：

- **临时缓解（运维手册，立即可执行）**：部署后手动记录 `-issue-server-cert` 的签发时间，设一个 25 天左右的提醒，到期前手动重新执行签发流程并重启 Gateway（拉起 `registry-init` 对应的一次性任务或手动跑同样的命令）。
- **根治需要改代码**：给 `registry-init` 加一个周期性重签的伴生任务，或者让 Gateway/Registry 自己在证书临近到期时自动续期（类似节点证书已经有的 `RenewCertificate` 续期路径，只是这里签发的是服务端证书而不是客户端 mTLS 证书）。这是一处具体、范围明确的后续任务，不在本次 A02 交付范围内，建议单独立项而不是顺手在本文档相关的收尾里做掉。

## 五、恢复演练运维手册（汇总）

以下是 A02 演练验证过的操作序列，写成可以照做的手册，补进 `deploy/database-recovery.md` 已经建立的文档体系（该文档专注数据库，本节专注 Registry 与对象存储，两者合起来才是完整的平台灾备，回应 STATUS.md"Job 重启测试不能替代整个平台灾备"这句话）：

### Registry 数据备份与恢复

1. 备份：对运行中的 Registry，`tar -czf registry-backup.tgz -C <data-dir 的父目录> <data-dir 名称>`（可以带进程运行时做，因为读的是文件系统快照，不需要停服务；但要接受备份点可能落在"两次写操作之间"这种通常无害的窗口）。
2. 校验：`sha256sum` 记录备份文件本身的校验和，与数据库备份的既有规范一致。
3. 恢复：停止 Registry 进程 → 清空/替换 `-data-dir` → 解压备份 → 重新启动进程 → 用 `-mint-token`/`-revoke-token` 之类的只读或幂等 CLI 调用做一次连通性验证（不要用会改变状态的调用去"顺便测试"，除非确实需要）。
4. **备份点之后发生过的节点禁用/审批操作，必须对照独立保留的运维安全记录人工重放**——与数据库恢复后"必须重放吊销"是同一类要求（`database-recovery.md:70`），Registry 这边同样成立，且目前没有代码层面的保护,全靠运维流程。

### 对象存储备份与恢复

1. 根据实际后端选择对应的备份方式：Local 后端就是文件系统备份（`tar`/`rsync`/文件系统快照均可）；S3/WebDAV 后端的备份委托给该存储服务自己的机制（本仓库不提供、也不该重新发明对象存储厂商已有的备份能力）。
2. 恢复后**必须**跑一次对账：拿 `job_artifacts` 表里未过期记录的 `storage_key` 逐条探测对象是否存在（可以用现有 `objectstore.Backend.Open` 或后端自带的 HEAD 类操作，不需要下载整个文件）,记录缺失的产物 ID,提前告知受影响的租户,而不是等他们自己发现下载 404。
3. 如果对象存储的恢复点晚于数据库（对象存储没有出问题，数据库回退了），检查数据库里已经不存在、但对象存储里仍然保留的产物,评估是否需要清理——目前没有自动化工具,本次演练已经证明这种悬空对象是会真实出现的,不是理论场景。

### 密钥轮换

见第三节的硬切换步骤;逐项密钥重复该流程,不要一次性同时轮换多个密钥,以缩小故障排查范围。
